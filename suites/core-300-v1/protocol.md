# 每模型 300 题基准：运行与评分协议

## 1. 比较单位

一个“模型配置”指模型权重、量化格式、推理运行时和采样参数的完整组合。每个配置必须运行清单中的同一批 300 题：150 题代码和 150 题困难推理。缺失题目不得静默删除，也不得用别题替换。

公开清单按题号排序；`index` 是公开清单中的 1–300 顺序，不是运行先后顺序。历史盲测的模型顺序不属于公开清单。

## 2. 共同输入与生成边界

- 每个模型配置使用完全相同的题目编号和提示词哈希。
- 每题独立请求，不携带上一题上下文。
- 温度为 0，单请求串行运行，不做基于答案质量的语义重试。
- 每题最大输出为 `8K tokens`，清单中的精确值为 8192。
- 截断、没有要求格式的最终答案、代码候选缺失和官方代码测试失败都计为模型失败。
- 传输错误与模型失败分开记录；传输错误不得伪装成模型 0 分。

不同模型家族使用的推理运行时可能不同，因此墙钟时间和生成速度不能只归因于模型权重。能力比较使用同题、同提示词和同评分规则；运行时差异必须随结果披露。

## 3. 代码题评分

150 题代码由 75 题 HumanEval+ 和 75 题 MBPP+ 构成。模型必须只返回一个完整 Python 代码块。评分使用 [`sources.json`](./sources.json) 固定的 EvalPlus 版本与对应官方测试；不使用大模型裁判。

解析不到单一代码候选、代码无法执行、超时或任一官方测试失败，均判为失败。评分器故障必须留在基础设施错误栏，不得更改模型原始输出后重新冒充首次结果。

## 4. 困难推理评分

150 题来自 MMLU-Pro。模型收到题目和全部选项，要求最终只输出：

```text
FINAL=<option letter>
```

评分只接受规范化后的精确选项字母。缺少最终标记、输出无效选项或截断均判为失败。

## 5. 配对统计

同一道题在两个模型配置上的成功或失败构成一对。比较时至少报告：

- 双方各自答对数与准确率；
- 一方独赢、另一方独赢的题数；
- 双侧精确 McNemar 检验；
- 代码与困难推理分项结果；
- 缺失、传输错误、截断和无最终答案数量。

McNemar 检验是只利用“同题上一方对、另一方错”的不一致样本，判断两个配对成功率是否有可检测差异的方法。没有达到显著性，不等于已经证明两个模型等效。

## 6. 原始同源量化对照的额外控制

最初的 Qwen3.8-27B 对照使用同一个未量化母模型直接生成两份 GGUF 文件。GGUF 是 `llama.cpp` 常用的本地模型文件格式：

- `Q4_K_M`：4-bit GGUF 量化配置；
- `Q8_0`：8-bit GGUF 量化配置。

两者统一使用 `llama.cpp` 代码版本 `0177dcc7300bad8914bb838baabce87899812491`、随机种子 20260821、上下文长度 `256K tokens`（262,144 tokens）、单流、关闭推测解码，并使用相同的 8-bit 键值缓存。后续跨模型结果仍复用同一批题和评分规则，但各自运行时身份以对应实验记录为准。
