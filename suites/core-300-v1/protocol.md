# 每模型 300 题基准：运行与评分协议

## 1. 比较单位

一个“模型配置”指模型权重、量化格式、推理运行时和采样参数的完整组合。每个配置必须运行清单中的同一批 300 题：150 题代码和 150 题困难推理。缺失题目不得静默删除，也不得用别题替换。

公开清单按题号排序；`index` 是公开清单中的 1–300 顺序，不是运行先后顺序。历史盲测的模型顺序不属于公开清单。

## 2. 共同输入与生成边界

- 每个模型配置使用完全相同的题目编号和提示词哈希。
- 每题独立请求，不携带上一题上下文。
- 温度为 0，单请求串行运行，不做基于答案质量的语义重试。
- 每题最大输出为 `8K tokens`，清单中的精确值为 8192。
- 截断、没有要求格式的最终答案、代码候选缺失和官方代码测试失败都计为模型失败。
- 传输错误与模型失败分开记录；传输错误不得伪装成模型 0 分。

不同模型家族使用的推理运行时可能不同，因此墙钟时间和生成速度不能只归因于模型权重。能力比较使用同题、逐字相同的用户提示词和同评分规则；运行时及平台系统上下文差异必须随结果披露。

## 3. 代码题评分

150 题代码由 75 题 HumanEval Plus（HumanEval 增强版，HumanEval+）Python 函数生成基准，以及 75 题 Mostly Basic Python Problems Plus（基础 Python 编程题增强版，MBPP+）构成；两个加号都表示增加了更强测试。模型必须只返回一个完整 Python 代码块。评分使用 [`sources.json`](./sources.json) 固定的开源代码执行评测器（EvalPlus）版本与对应官方测试；不使用大模型裁判。

解析不到单一代码候选、代码无法执行、超时或任一官方测试失败，均判为失败。评分器故障必须留在基础设施错误栏，不得更改模型原始输出后重新冒充首次结果。

## 4. 困难推理评分

150 题来自 Massive Multitask Language Understanding Pro（多学科语言理解专业难度版，MMLU-Pro）选择题推理基准；Pro 表示更困难的增强版本。模型收到题目和全部选项，要求最终只输出名为 `FINAL` 的最终答案字段，等号后填写选项字母：

```text
FINAL=<option letter>
```

评分只接受规范化后的精确选项字母。缺少最终标记、输出无效选项或截断均判为失败。

## 5. 配对统计

McNemar 检验只利用“同题上一方对、另一方错”的不一致样本，判断两个配对成功率是否有可检测差异。没有达到显著性，不等于已经证明两个模型等效。

同一道题在两个模型配置上的成功或失败构成一对。比较时至少报告：

- 双方各自答对数与准确率；
- 一方独赢、另一方独赢的题数；
- 双侧精确 McNemar 检验；
- 代码与困难推理分项结果；
- 缺失、传输错误、截断和无最终答案数量。

## 6. 原始同源量化对照的额外控制

最初的 Qwen3.8-27B 对照使用同一个未量化母模型直接生成两份 GGML Universal File（GGML 通用文件，简称 GGUF）模型文件；`3.8` 是模型系列版本标识，`27B` 表示约 270 亿参数。GGML 是开源本地推理引擎 `llama.cpp` 所用底层张量库的项目名；这里提到 GGUF 是为了说明本地加载的模型文件格式：

- `Q4_K_M`：`Q4` 表示以 4-bit 为主，`K` 表示 K-quants 分块混合量化家族，`M` 表示 Medium（中等）配方；
- `Q8_0`：`Q8` 表示 8-bit，`0` 表示基础配方。

两者统一使用 `llama.cpp` 的同一份源码提交；40 位十六进制提交标识为 `0177dcc7300bad8914bb838baabce87899812491`。两者还统一使用随机种子 20260821、上下文长度 `256K tokens`（262,144 tokens）、单流、关闭推测解码，并使用相同的 8-bit 键值缓存。后续跨模型结果仍复用同一批题和评分规则，但各自运行时身份以对应实验记录为准。

## 7. 渠道扩展结果的隔离规则

如果某个产品入口完成了同一批 300 题，并能证明题目身份、逐字相同的用户提示词与评分器完全一致，但平台系统上下文不同，或没有开放温度、随机种子、最大输出长度或不可变后端版本，则该结果只能标为“同题同判分的渠道扩展对照”。它必须与遵守第 2 节全部生成边界的严格协议主表分开，逐项披露不可控参数，不比较速度，也不得改写为固定模型版本在严格同协议下胜出。
